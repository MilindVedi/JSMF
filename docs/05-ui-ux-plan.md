# UI/UX Plan — Mock Prototype Stage

This document is the definitive design and frontend architecture plan for the current mock UI prototype described in [V1 Scope](./02-v1-scope.md). Everything described here concerns the frontend-only prototype: static and mocked data, no real backend, and no real authentication or payments, exactly as scoped in the "Current Stage" section of [V1 Scope](./02-v1-scope.md). Where this document refers forward to a real backend or real content, that is describing how the mock is deliberately shaped to make that later transition easy — not something implemented now.

This document has been updated to match what was actually built, not just what was originally planned — a few details changed during implementation, and those are called out explicitly (in the technology table, the component structure, the mock data model, and state management) rather than left to drift silently out of sync with the code.

The repository this plan targets was confirmed empty before work began — no prior commits, no scaffolding — so this was a genuine from-scratch build. The available tooling was Node v20.19.0 with npm 10.8.2 and no yarn or pnpm, so the app was scaffolded with `npx create-next-app@latest` using npm as the sole package manager.

**Repository layout.** The Next.js application lives in this repository under [`web/`](../web), not at the repository root — see the root [`README.md`](../README.md) for why: the repository is a small monorepo, and `web/` sits alongside `docs/` and (eventually) `backend/` and `mobile/` folders for the pieces described in [Architecture](./03-architecture.md). Every path below (e.g. `src/app`, `src/components`) is relative to `web/`, i.e. the landing page actually lives at `web/src/app/(marketing)/page.tsx`.

## Design Principles & Direction

JSMF's mock UI is designed to feel premium, modern, clean, and unmistakably medical-academic and professional, while remaining fast to use. It is explicitly **not** a visual copy of Marrow or PrepLadder — both the palette and typography decisions later in this document are chosen in part specifically to avoid resembling either competitor. Because this is a study product where a single sitting can mean working through dozens or hundreds of questions in one session, a recurring design constraint throughout this plan is that the interface must hold up over long, repeated use: color choices, typography, and layout decisions are all made with sustained readability and reduced visual fatigue in mind, not just first-impression polish.

## Technology Choices for the Mock

| Choice | Reasoning |
|---|---|
| **Next.js App Router** | Non-negotiable for a new build — the Pages Router is legacy-maintenance mode at this point. More importantly, the App Router's nested layouts are the exact mechanism needed to solve the single hardest layout problem in this product: the practice/question-solving screen must **not** inherit the sidebar-and-topbar app shell that every other authenticated page uses. Route groups solve this cleanly, without prop-drilling or conditional rendering to fake a different shell. |
| **TypeScript, strict mode** | Used throughout, with a `src/` directory layout (`src/app`, `src/components`, `src/data`, `src/lib`, `src/store`, `src/types`) to keep the repository root clean, and an `@/*` import alias for ergonomic imports. |
| **Tailwind CSS v4** | Its CSS-first configuration model — a `@theme` block inside `globals.css` — is exactly what is needed to define JSMF's custom design-token palette as CSS variables, and that integrates natively with shadcn/ui's own CSS-variable-based theming model. |
| **shadcn/ui** | Chosen over both hand-rolling every primitive and over adopting a heavy, opinionated component library such as MUI, Chakra, or Ant Design. shadcn/ui components are copied directly into the repository (`src/components/ui`), so there is no black-box runtime dependency and no fight against a foreign design system when trying to establish JSMF's own premium visual identity — every primitive is just Tailwind plus an accessible headless library, fully restyleable. **Implementation note:** the shadcn CLI, run against this project's dependency versions, generated primitives built on [Base UI](https://base-ui.com) (`@base-ui/react`) rather than classic Radix UI — Base UI is the same team's newer headless library, with a very similar Root/Trigger/Content composition pattern, but it replaces Radix's `asChild` prop with a `render` prop and a few hook names differ. This is noted here because it matters for anyone extending these components later; it did not change which primitives were used or how they're composed at the call-site level. The project uses Dialog (Report Question modal), Popover (Question Palette, keyboard-shortcuts help, filter menus), Tabs (switching between exams), Accordion (FAQ), Checkbox and Sheet/Drawer (mobile filter panel and mobile sidebar), Dropdown Menu (the topbar's account menu), and Toast via `sonner` — all accessible and keyboard-navigable out of the box, which matters directly for the fast, keyboard-friendly navigation the solving screen needs. MCQ options and multi-select filters are, deliberately, **not** built on shadcn's RadioGroup/Select — see Component Structure and Mock Data Model below for why. |
| **lucide-react** | The icon set, chosen because it pairs natively with shadcn/ui, is tree-shakeable, and keeps a consistent single-stroke style across the whole product. |
| **Fonts, via `next/font/google`** | See the dedicated typography discussion under Design Tokens below; in summary, `Plus Jakarta Sans` for UI and headings, `Source Serif 4` for reading content, and `JetBrains Mono` as a sparing accent for numerals. |
| **react-hook-form + zod** | Handles forms and their validation across the app (auth forms, filter forms, the custom test builder). |
| **recharts** | Powers the statistics and performance charts. |
| **zustand, nanoid, date-fns, next-themes, clsx / tailwind-merge** | Supporting utilities: zustand for state management (discussed in its own section below), nanoid for generating session IDs, date-fns for date handling, next-themes wired in from day one for a future dark-mode pass even though it is not fully polished in v1, and clsx/tailwind-merge for conditional class composition. |

## Full Route / Page Structure

Routes are organized using App Router route groups, which let different sections of the site have entirely different layouts while sharing one root layout:

```
src/app/
  layout.tsx
  globals.css

  (marketing)/
    layout.tsx                        # MarketingHeader + MarketingFooter
    page.tsx                          # "/" Landing page (single long-scroll, anchor-nav sections)
    pricing/page.tsx                  # "/pricing" Public plan comparison
    about/page.tsx                    # "/about" Company blurb
    contact/page.tsx                  # "/contact" Email + response-time info
    privacy/page.tsx                  # "/privacy" Placeholder privacy policy
    terms/page.tsx                    # "/terms" Placeholder terms of service

  (auth)/
    layout.tsx                        # centered card, logo only, no nav
    login/page.tsx
    signup/page.tsx
    forgot-password/page.tsx
    reset-password/page.tsx           # mock: no real token/email flow

  (app)/
    layout.tsx                        # AppShell: Sidebar + Topbar, auth-gated
    dashboard/page.tsx
    question-bank/page.tsx            # filters live in URL search params
    custom-test/new/page.tsx
    revision/page.tsx                 # revision hub: wrong-question modes + bookmarks + reinforce
    bookmarks/page.tsx                # full bookmark list, reached from Revision
    wrong-questions/page.tsx          # flat wrong-question list, superseded by Revision
    reinforce/page.tsx                # full correct-questions list + all/recent/not-revisited filter, reached from Revision
    history/page.tsx
    statistics/page.tsx
    subscription/page.tsx
    profile/page.tsx

  practice/
    layout.tsx                        # minimal focused chrome — sibling to (app), NOT nested in it
    [sessionId]/
      page.tsx                        # "/practice/[sessionId]?i=<index>" the solving screen
      results/page.tsx                # "/practice/[sessionId]/results"
      review/page.tsx                 # "/practice/[sessionId]/review?i=&filter=" read-only review
```

**The review screen** (`practice/[sessionId]/review/page.tsx`) is a separate, read-only mode from the live solving screen, reached from a "Review answers" button on the results page. It reuses `QuestionCard`/`OptionButton` with `submitted` always `true` and a new `ReviewExplanationPanel` (a three-state sibling to `ExplanationPanel` — correct / incorrect / not-attempted — kept separate so the live-practice component's boolean `isCorrect` contract stays untouched). Both the current filter (All/Correct/Incorrect/Unattempted) and the current question index live in the URL (`?i=&filter=`), so a link into a specific filtered view is shareable and survives a refresh. The filter defaults to "Incorrect" whenever the session has any wrong answers — the whole point of opening review from a completed test — and a horizontal `ReviewNavStrip` beneath the header shows only the questions matching the active filter (each a small numbered, ✓/✕-coded chip), not the full session, so the strip and the Previous/Next controls always agree on what's currently in view.

The key structural decision here is that `practice/` sits at the same level as `(app)` and `(marketing)` rather than being nested inside `(app)`. This is what allows it to have its own minimal layout — described under Navigation & App Shell below — while still sharing the root layout, without the practice screen ever picking up the sidebar and topbar chrome that every other logged-in page uses.

### Question-Solving as a Session, Not a Single-Question Route

A second important structural decision is that question-solving is modeled around a **session**, not a single-question page. A `TestSession` is shaped as `{ id, mode, questionIds[], config, flags, attempts }`, and every entry point into practicing questions — browsing the question bank, launching a custom test, resuming bookmarks, resuming wrong questions, or clicking a row in a results list — funnels into creating (or reusing) a session and redirecting to `/practice/[sessionId]`.

Concretely: clicking a row in the Question Bank results starts a session containing the entire current filtered result set, positioned at the clicked question. Submitting the Custom Test builder creates a session with `mode: 'custom-test'` and `config.timed`. The "Practice these" buttons on Bookmarks and Wrong Questions each create a session from that respective list. The current position within a session is tracked as a URL search parameter (`?i=4`), so it is shareable and survives a refresh. Finishing a session redirects to its results page, and the History section lists every completed session — both plain practice and custom-test — with a badge indicating which type it was.

**The results page adapts its wording and content to how the session was started**, rather than always reading "Test Result": a Custom Test says "Test completed," a Question Bank session keeps its subject/mode label, and a Revision session says "Revision complete" — driven by `session.mode`, not a separate flag. Each question row is numbered (`Q1`, `Q2`, …) so a student can act on "review Q7." A per-subject performance breakdown appears only when the session actually spans more than one subject (a single-subject Question Bank session doesn't need it). The primary CTA is "Review answers," leading to the read-only review screen described above, with a status pill underneath reading "N to review" (colored to match whichever stat tile — Incorrect/Unattempted/Correct — it's summarizing) or "All correct."

**Question Bank browsing** gained a status filter (`StatusTabs`: All Questions/Correct/Incorrect/Unattempted, with live counts — labeled "All Questions" rather than a bare "All" specifically to avoid reading as a second, competing "All" next to "All Exams" in the filter row above it) and a per-row status indicator (a small ✓/✕/○ dot), both derived the same way as Revision's slices — from `getQuestionStatusMap`, not a separately stored field. Each row also shows its position in the current filtered list as a subtle `Q{n}` label, so a specific question is easy to reference in conversation ("check Q18"). **Statistics** gained a "question bank coverage" metric (share of the whole bank attempted at least once) distinct from accuracy, specifically because a student can score well on repeated custom tests while leaving most of the bank untouched — the two numbers are meant to be read together, not as duplicates of each other.

**The Exam filter is multi-select, not single-select**, on the same "empty selection means unfiltered" convention as Year/Subject/Topic: `QuestionFiltersState.examIds: ExamId[]` (renamed from a single `examId: ExamId | "all"`), with an empty array meaning "All Exams" and multiple ids meaning an OR across them (e.g. NEET-PG + FMGE). This matters for students preparing for more than one exam, who previously had to run separate filtered passes per exam. The dedicated `ExamTabs` (a segmented `Tabs` control) was removed and replaced by the same `MultiSelectPopover` used for Year/Subject/Topic, extended with two new optional props: `allOption` (renders a pseudo "All Exams" row above a divider, checked whenever the selection is empty or covers every option, and always resets to empty when clicked) and `triggerLabel` (an override so the trigger shows the actual selection — "All Exams," "NEET-PG," "NEET-PG + FMGE," or "3 exams" — rather than a generic label + count badge). Unifying Exam onto the same dropdown-button component as the other three filters was also the fix for the filter row previously reading as "merged" — the old segmented Exam control had a visually distinct shape from the Year/Subject/Topic pill buttons sitting right next to it; all four are now the same control.

**Exam access is not gated in the mock UI.** The intended real-product behavior — a locked exam shows a 🔒 and clicking it prompts "Upgrade to All Access" for a Single Exam Pro user, reading from that plan's `entitlements.examIds` (see [Architecture](./03-architecture.md)) — is deliberately not built here, because the mock's one demo user is seeded on the `all-access-pro` plan, which already entitles all three exams; there is nothing to gate against. This is noted here as a known gap for whenever a plan-aware demo user (or the real backend) exists, not an oversight in the current filter UI.

## Navigation & App Shell

The product uses four distinct navigational contexts, each with a shell deliberately scoped to what that context needs:

- **Marketing shell.** A sticky header carrying the logo, anchor links to sections of the landing page, and Login/Sign Up buttons. The footer uses a column layout, and further down the landing page there is a small "Coming Soon: Courses · PDFs · Notes" strip that signals the broader future product surface described in [Product Vision](./01-product-vision.md) without implying any of it exists yet. The footer's "Company" column (About, Contact, Privacy Policy, Terms of Service) originally pointed every link at `href="#"` — the pages simply didn't exist yet. They now route to real (if intentionally lightweight) pages under `(marketing)/about`, `/contact`, `/privacy`, `/terms`, each following the same centered-hero-plus-body layout as `/pricing` rather than introducing a new page pattern for four low-traffic pages.
- **Auth shell.** A centered `AuthCard`, showing only the logo, a link back to the marketing homepage, and a toggle link between the login and signup forms — deliberately free of any app navigation.
- **App shell.** A collapsible left sidebar paired with a topbar, gating every logged-in, non-practice page. The sidebar's sections, in order, are: Dashboard, Question Bank, Custom Test, Revision, History, Statistics — then a divider — Subscription, Profile. That order deliberately mirrors the product loop of practise → identify weaknesses → revise, which is why Revision sits above History and Statistics rather than being grouped with them as reporting. **Revision is a hub, not a list:** it consolidates what were previously two separate sidebar entries, presenting wrong questions under four slices — all wrong, recently wrong (last 7 days), never corrected (attempted but never once answered correctly), and by subject — alongside a bookmarks section, each with its own "practise these" entry point. The standalone `/bookmarks` and `/wrong-questions` pages still exist and are linked from the hub, so nothing became unreachable.

**The History page (`history/page.tsx`) filters its session list by session type and time period** without touching the four overview stat tiles (Attempted/Correct/Incorrect/Unattempted) above them — those reflect overall progress across the whole question bank via `getStatistics`, which is unrelated to which past sessions happen to be visible in the filtered list below, so filtering the list would misleadingly suggest the tiles were scoped to it too. The session-type filter is a `Tabs` row (All / Question Bank / Custom Test / Bookmarks Revision / Wrong Questions Revision) with a live count per tab, and the time-period filter (All time / Last 30 days / Last 7 days) is the same bordered-pill-button pattern used elsewhere in the app (e.g. the Custom Test builder's Include/Ordering controls) rather than another `Tabs` instance, since two adjacent `Tabs` rows read as one control. **The Statistics page's "Wrong questions" / "Bookmarks" link-out row gained a third "Reinforce" entry** pointing to `/reinforce`, reusing `stats.correct` (already computed by `getStatistics`, and equal in meaning to `getCorrectQuestionFacets(...).all.length`) rather than importing a second selector for the same count.

**A third, deliberately smaller "Questions you answered correctly" section sits below Bookmarked**, mirroring the wrong-questions slicing (`getCorrectQuestionFacets` in `lib/selectors`, the mirror of `getWrongQuestionFacets`) but for questions already answered correctly — all/recently-correct/not-revisited. The hub itself shows only the **not-revisited** slice (falling back to all-correct if that's empty), capped at 5 rows with a "View all N" link to the standalone `/reinforce` page (which has the full list and the three-way filter) — this was an explicit product call: reinforcing what a student already knows matters less than fixing what they got wrong, so this section is plain text + an outline button, not a bordered `Card` with a `Tabs` filter like the two sections above it, and it doesn't appear at all when there are no correct answers yet. The three summary stat tiles at the top of the hub gained a matching third tile ("Reinforce · what you know"), so the page names all three things it now covers without implying they're equally weighted — that weighting lives in the sections below, not the tiles. At medium widths the sidebar collapses to an icon-only rail, and on mobile it becomes a slide-over Sheet. The topbar carries the page title or breadcrumb on the left, and a dynamically-styled streak chip (`TopbarStreakChip`, see Streak & Engagement System below), plan badge, and avatar dropdown on the right — the account dropdown also carries "Visit JSMF website" (opens the marketing site in a new tab), deliberately placed there rather than as its own sidebar entry so it doesn't compete with the app's own navigation.
- **Practice shell.** This is deliberately the most minimal of the four. It consists of a single slim top bar: an exit / "Save & Exit" control and the logo mark on the left, "Question 7 of 20" together with a thin progress bar in the center, and — when the session is timed — a timer alongside bookmark and flag quick-icons on the right. There is no sidebar and no footer. The reading content itself sits in a single column capped at roughly 720–760px and centered on the page, which is the single highest-leverage readability decision on this screen. A sticky `PracticeActionBar` at the bottom of the screen holds Previous, Next, Submit, and Finish controls, plus a trigger for the `QuestionPalette` — a popover grid, color-coded for answered/flagged/unanswered/current, that is deliberately kept on-demand rather than permanently visible on screen, as a quieter alternative to how competitor products handle the same idea. Keyboard shortcuts are supported throughout this screen (1–4 to select an option, Enter or N for next, P for previous, B to bookmark, F to flag) and are discoverable via a small "?" popover rather than being hidden.

## Component Structure

Components are organized by concern into the following folders: `components/ui` (the shadcn primitives), `components/layout` (`Sidebar`, `SidebarNav`, `Topbar`, `TopbarStreakChip`, `StreakFlyOverlay`, `MarketingHeader`, `MarketingFooter`, `AuthCard`, `PracticeTopbar`), `components/marketing`, `components/practice`, `components/question-bank`, `components/dashboard`, `components/history`, `components/statistics`, `components/subscription`, `components/common`, and `components/dev` (tools for reviewing the mock, not part of the real product — see the theme picker note below).

The key reusable components built across these folders are: `QuestionCard`, `OptionButton` (with default, selected, correct, incorrect, and muted/disabled states), `ExplanationPanel` and `ReviewExplanationPanel` (the three-state review-only sibling described above), `ProgressIndicator` (via shadcn's `Progress`), `QuestionPalette`, `ReviewNavStrip`, `PracticeActionBar`, `BookmarkButton`, `FlagButton`, `ReportQuestionModal`, `TimerDisplay`, `KeyboardShortcutsPopover`, `FilterPanel`, `ActiveFilterChips` (spells out the currently-selected exam/year/subject/topic filters as removable chips, shared by the Question Bank and Custom Test builder), `StatusTabs` (All Questions/Correct/Incorrect/Unattempted, Question Bank only), `MultiSelectPopover`, `QuestionListRow`, `Sidebar`, `Topbar`, `TopbarStreakChip`, `StreakFlyOverlay`, `StatCard`, `QuickActionCard`, `StreakCard`, `ContinuePracticeCard`, `OnboardingDashboard` (described below), `SessionHistoryRow`, `TestSummaryCard`, `PricingCard`, `CurrentPlanBanner`, `SubjectPerformanceChart`, `AccuracyTrendChart` (now plots both a session's own accuracy and the running cumulative accuracy, as two lines), `DonutBreakdown`, `EmptyState`, `PageHeader`, `SubjectBadge`, `ExamBadge`, `Logo`, `FigurePlaceholder`, and `ThemePalettePicker` (a floating, dev-only widget — see Design Tokens below).

**The dashboard's "Continue where you left off" card and streak card were split out of a single generic card into two purpose-built components.** `ContinuePracticeCard` reads whichever session is in progress (or, if none, the most recently completed one) and describes its actual scope in the label — e.g. "Question Bank · NEET-PG · Pathology · 10 questions" — falling back to a bare count only when naming every exam/subject involved would be noise (`scopeLabel()`/`scopeDescription()` in that file). `StreakCard` replaced the earlier `TodayProgressCard`/`StreakWidget` pair entirely — see Streak & Engagement System below for what it does.

**This card follows a strict, non-arbitrary decision tree, not a "mix":**

```
Is there an unfinished session?
  YES → resume that exact session (deep-link into it at the next unanswered question)
  NO  → "Start practising" — Question Bank | Custom Test entry points, no resume UI at all
```

- **Which session counts as "the" unfinished one.** A user could in principle leave more than one session incomplete (start a Question Bank session, navigate away, then start a Custom Test). The dashboard resolves this by `startedAt`, always resuming the **most recently started** incomplete session — never just the first one found in the sessions store, which would have resumed an arbitrary older abandoned session instead.
- **The exact resume point.** The link target's `?i=` index comes from `getNextUnansweredIndex()` (`lib/selectors`) — the first question in the session with no attempt yet — not from `answeredCount`. A plain count would be wrong the moment a question is answered out of the original order (e.g. jumping around via the question palette), silently resuming at the wrong question.
- **The label always names the real session type.** `scopeLabel()` prefixes with the session's own `label` field (`"Question Bank"`, `"Custom Test"`, `"My Bookmarks"`, etc. — set once by whichever screen called `useStartSession`, see State Management), so the card never has to guess or blend one mode's presentation with another's; what launched the session is what's shown and what's resumed.

**MCQ options are deliberately not built on shadcn's RadioGroup.** `OptionButton` is a plain button (with `role="radio"` for accessibility) so it can carry the richer set of visual states a solved question needs — default, selected-before-submit, correct, incorrect-selection, and muted-after-submit — which don't map cleanly onto a standard radio control's checked/unchecked states.

**Question Bank and Custom Test filtering are built on a custom `MultiSelectPopover`** (a `Popover` containing a `Checkbox` list), not shadcn's `Select`, because Exam, Year, Subject, and Topic all need multi-selection with a visible selected-count badge (Exam via its `allOption`/`triggerLabel` props, described above) — a single shared component for all four, rather than a one-off single-select control for Exam.

**The Custom Test builder (`custom-test/new/page.tsx`) never lets a configuration silently underdeliver.** Filters narrow a `pool` of questions; on the main page, "Number of questions" reads the true available count from that pool and offers four ways to pick a value — preset buttons (10/20/30/50), an "All" button that tracks the live available count rather than freezing it, a bordered number input, and a `Slider` (`components/ui/slider.tsx`, a shadcn-style wrapper over `@base-ui/react/slider`) — all four kept in sync through one `count`/`useAll` state pair. Presets above the available count are disabled outright; the number input blocks decimal/negative/exponent keystrokes on keydown and, if a typed value exceeds what's available, is silently clamped back down to the true max on blur (not while typing, so the ⚠️ "Only N questions match" warning has a chance to show first). The Start button and a highlighted, bordered configuration summary ("20 questions · NEET-PG · General Medicine · 20 min timed") both derive from `Math.min(selectedCount, availableCount)` rather than a separately-tracked clamped value, keeping the display and the actual `startSession` call impossible to disagree with each other.

Clicking Start opens a confirm `Dialog` ("Ready to start?") rather than launching immediately — this is where the remaining, genuinely optional choices live: an "Include" toggle (All questions / Unattempted only, filtered via `getQuestionStatusMap`), an "Ordering" mode (Random / Unattempted first / Incorrect first / Bookmarked first — the last three reorder the pool to prioritize that subset before filling the remainder randomly, rather than acting as a strict inclusion filter), and a "Test name" field that sets the session's `label` (defaulting to "Custom Test" when left blank). Moving these into the confirmation step, rather than three more cards on the main page, keeps the primary flow to Filters → Number of questions → Timed test, with everything genuinely optional deferred to the moment the student is already committing to start. The Exam filter's subscription-based locking (All Access Pro sees a multi-select, Single Exam Pro would see a fixed/locked exam) remains a documented-but-undeferred behavior — see "Subscription / Entitlement Modeling" in `03-architecture.md` — since the single mock user is always on `all-access-pro` and there is nothing to gate against yet.

**Timed Test duration is derived from a pace (minutes per question), not picked from a fixed list of totals.** Real exams already run close to 1 minute/question (NEET-PG ≈ 63s, FMGE ≈ 60s, INI-CET ≈ 54s), so `MIN_MIN_PER_QUESTION = 1` is the realistic-pace floor a student should never be forced under. The ceiling, `MAX_MIN_PER_QUESTION = 1.5`, caps relaxed practice at 1.5× that baseline — generous enough to remove real time pressure without making the timer meaningless (e.g. 10 questions → 10–15 min, 20 → 20–30 min, 50 → 50–75 min, 100 → 100–150 min). The stored state is the pace itself (`minPerQuestion`, adjustable via the same number-input-plus-slider pairing used for question count), and duration in minutes is always `Math.round(finalCount * minPerQuestion)` — so the range automatically stays proportional as the question count changes, with no separate effect needed to re-clamp it. A fixed extra buffer (e.g. "+10 minutes" regardless of question count) was considered and rejected: it doesn't scale, so it would matter a lot for a 10-question test and be meaningless for a 100-question one.

One component is worth calling out specifically for its purpose rather than just its shape: `QuestionPreviewDemo`, which lives on the landing page. It is a genuinely interactive, unauthenticated mini-instance of the question-solving UI, built around a real question pulled from the seeded question bank — clicking an option produces an instant correct/incorrect result and reveals the explanation, without creating a real session. The intent is that this is materially more convincing to a prospective user than a static screenshot of the product would be.

## Collections

**A Collection is a named, curated set of questions** (`Collection` in `types/index.ts`: `id`, `name`, `description?`, `questionIds`, `createdAt`) — a distinct concept from a bookmark. A bookmark is "save this one question for later"; a collection is a themed group ("High-Yield Pharmacology," "Toughest Questions") meant to be browsed, filtered by, and practised as a unit. `useCollectionsStore` (`store/collections-store.ts`) follows the exact same seed/reset pattern as bookmarks and sessions: `seedCollections()` no-ops if any already exist (so real data is never clobbered by a later login), `resetCollections()` hard-clears on signup, and both are wired into `auth-store.ts` alongside the other stores. `lib/seed-demo-data.ts`'s `buildSeedCollections()` seeds eight plausible collections spanning multiple subjects and both a "hard" and an "easy" difficulty-based set, so the feature doesn't look sparse with only a handful of entries. **There is deliberately no create/rename/delete UI for the collections themselves** — that's tracked as a future addition in `docs/07-future-scope.md`. What the store does support is `toggleQuestionInCollection(collectionId, questionId)`, adding/removing one question from an existing collection — this is the one supported mutation, exposed via the "Add to collection" button next to every question row (see below), deliberately narrower than full collection CRUD.

Collections show up in four places, each reusing the same two selectors (`getCollectionStats`, `getQuestionsInCollections` in `lib/selectors`) rather than four different ad-hoc computations:

- **Revision hub** (`revision/page.tsx`): the top stat-tile row grew from 3 cards to 4 (`sm:grid-cols-2`, two per row) — Wrong / Bookmarked / Reinforce / Collections — and **every tile is now a clickable in-page anchor** (`<a href="#…-section">`) rather than a static stat, jumping to its own section further down the page (`scroll-mt-20` on each section keeps it clear of the sticky topbar). The "Questions you answered correctly" (Reinforce) section was later restyled from its original lighter, borderless treatment into the same bordered `Card`/`CardHeader`/`CardContent` structure as every other section, since having one visually distinct section among four otherwise-identical ones read as a mistake rather than an intentional hierarchy. The Collections section also uses this same `Card` treatment, but its collection picker is **single-select** (`MultiSelectPopover`'s `singleSelect` prop — clicking an option replaces the selection instead of toggling it, and there's no "clear"/"all" state), defaulting to whichever collection has the most recent `createdAt`. This is a deliberate difference from the filter usage below: this section browses one collection at a time rather than filtering across many, so "select several" or "select none" aren't meaningful states here the way they are for a search filter. All four sections are independently collapsible via a shared `CollapsibleSection` wrapper (a chevron button built into the title) — a plain local toggle rather than the `Accordion` primitive, since these are `Card`-based sections with their own rich header content (sort dropdowns, practise buttons) rather than the simple text-trigger list `Accordion` is built for. Open/closed state is lifted to the page (an `openSections` record keyed by section, not owned inside `CollapsibleSection` itself) specifically so the four stat tiles above can *expand* a section on click, not just scroll to it — each tile's `href="#…-section"` anchor still does the native scroll, but its `onClick` also flips that section open if it was collapsed. Each section's `headerExtra` is a function of `open` rather than a plain node, so its sort dropdown can be hidden while collapsed — a control for choosing how to view content that isn't visible is just noise on a collapsed card, whereas the Practise button stays visible either way (it's an action, not a view option, and the whole point of collapsing a section is to still be able to act on it — e.g. "Practise 9" — without reopening it). The four Practise buttons/labels across sections were also unified to the same "Practise {n}" wording (previously "Practise all {n}" on Bookmarked and "Practise these {n}" on Wrong were inconsistent with the other two). Wrong Questions and Bookmarked start expanded; Reinforce and Collections start collapsed — a deliberate priority ordering, not an arbitrary default, since fixing mistakes and revisiting bookmarks are the more actionable, higher-intent parts of revision than reinforcing what's already known or browsing curated sets.

`CollapsibleSection`'s `CardHeader` initially used `flex-row items-center justify-between` classes to put `headerExtra` on the right — the same mistake noted elsewhere in this doc: `CardHeader` is `display: grid` by default, and `has-data-[slot=card-action]:grid-cols-[1fr_auto]` only activates a two-column layout when a `CardAction`-slotted child is actually present, so those flex classes had no effect and the action content rendered stacked below the title instead of beside it. Fixed by wrapping `headerExtra`'s return value in `CardAction`, letting `CardHeader`'s own `has-data-*` variant do the layout instead of fighting it with utility classes.

Each of the four sections also gained its own **search box** (`SectionSearch`, a small wrapper around the shared `Input` + a `Search` icon) filtering that section's question list by stem substring (`filterByStem` in `revision/page.tsx`) — independent per section, since "search within Wrong Questions" and "search within Collections" are different queries over different pools. It only appears once there's something to search (e.g. Bookmarked's box is hidden until at least one bookmark exists) and sits below any other filters, narrowing whatever they've already produced rather than replacing them. It does not feed back into a tab's own count badge (e.g. "Wrong 31" stays the exam/date-filtered total, not the further search-narrowed number) — the search box narrows what's *visibly listed*, the same way Question Bank's search box doesn't rewrite its other filter counts either. The Wrong section's "By subject" grouping filters each subject's own question list and drops any subject-group left with zero matches, rather than leaving it visible with an empty row.
- **Question Bank and Custom Test filters** (`filter-panel.tsx`, shared by both pages): gained a fifth `MultiSelectPopover`, "Collection" (only rendered when at least one collection exists), following the established "empty = unfiltered" convention — `getQuestionsInCollections` returns the input list untouched when nothing is selected, and restricts to the union of selected collections' questions otherwise. `active-filter-chips.tsx` shows a removable chip per selected collection.
- **Statistics** (`statistics/page.tsx`): the bottom link-out row grew from 3 cards to 4 (`sm:grid-cols-2`), adding a "Collections" card that links to `/revision#collections-section` — since Collections has no standalone route of its own (unlike Reinforce/Bookmarks), it links into the Revision hub's own section rather than duplicating the browsing UI on a second page.

The "Question bank coverage" card on Statistics is also clickable (`role="button"`, keyboard-activatable), opening a `Dialog` with the same overall coverage line plus a per-subject breakdown from the new `getSubjectCoverage()` selector (`lib/selectors`), sorted least-covered-first — the more actionable ordering for "what haven't I touched yet" than sorting by attempt count. This is a genuinely different question from `getStatistics().bySubject`, which only lists subjects with at least one attempt (right for an accuracy chart, since 0-attempt subjects have no accuracy to plot) — coverage needs every subject, including the ones still sitting at 0%, so it's computed as its own selector rather than reusing `bySubject`.
- **History** (`history/page.tsx`): the session-type `Tabs` row (All / Question Bank / Custom Test / Bookmarks Revision / Wrong Questions Revision) gained a rightmost "Collections" tab (shown only when at least one collection exists) — a pseudo-mode that isn't a real `SessionMode`, matching any session whose `filters.collectionIds` is non-empty, handled as a separate branch in the filter predicate rather than added to the `SessionMode` union itself. Separately, the page also gained a "Collection:" filter (multi-select, following the Question Bank/Custom Test "empty = unfiltered" convention, not the Revision hub's single-select-with-default) — filtering completed sessions by whether `session.filters?.collectionIds` intersects the selected collections. Both only produce results for sessions actually started with a collection filter active (Question Bank, Custom Test, or Revision's Collections section all now thread `collectionIds` through to `startSession`); the Collections *tab* answers "did any collection filter apply" while the Collection *dropdown* narrows to a specific one — deliberately two independent controls rather than merging them. The "Collection:" dropdown was originally a wrapping row of pill-buttons (one per collection) but was replaced with the same compact `MultiSelectPopover` used elsewhere, since the pill row grew unwieldy and inconsistent-looking as more collections were seeded. The time-period filter also grew a "Custom range" option alongside All time/Last 30 days/Last 7 days, using the shared `DateRangePicker` (see below) to filter sessions by `completedAt` day inclusively — a fourth, independent branch in the same filter predicate as the preset windows, not a separate control.

**Every question-list row across the app now carries a working Bookmark and "Add to collection" button, not just a decorative bookmark glyph.** This required restructuring `QuestionListRow` (`components/question-bank/question-list-row.tsx`): it used to be a single `<button>` wrapping the entire row (status dot, stem, a non-interactive bookmark icon, a trailing chevron), which left no valid way to nest a second real, independently-clickable control inside it — a `<button>` inside a `<button>` isn't valid HTML and base UI's own interactive elements assume they aren't nested either. The row is now a plain `<div>` whose primary "practise this question" click target is an inner `<button>` wrapping only the status dot and text content, with the actual `BookmarkButton` (reused as-is from `components/practice/bookmark-button.tsx` — the same component the practice screen's own bookmark control uses) and the new `AddToCollectionButton` (`components/question-bank/add-to-collection-button.tsx`, a `Popover` of checkboxes over `useCollectionsStore`'s collections, calling `toggleQuestionInCollection`) sitting as siblings after it, not descendants — so both are always real, working controls rather than needing `stopPropagation` gymnastics to fight a wrapping button. `AddToCollectionButton` renders nothing when there are no collections yet, matching the same "don't offer a control over an empty concept" convention as the Collection filter. Adopting this everywhere also meant retiring three bespoke, duplicated row implementations that had drifted out of sync with `QuestionListRow` (no Q# numbering, no status dot, no bookmark control at all) — `bookmarks/page.tsx`, `wrong-questions/page.tsx`, and `reinforce/page.tsx` now all render the same shared component instead of hand-rolled markup, so the next visual change to a question row only has one place to make it.

**Profile photo upload** (`profile/page.tsx`): a small camera-icon button overlaid on the avatar opens a hidden file input; the chosen image is read via `FileReader.readAsDataURL` and stored directly as `profile.avatarUrl` (capped at 2MB — purely a mock-side ceiling to keep the data URL from bloating localStorage, since there's no real upload endpoint to offload it to). A second "×" button appears once a photo is set, clearing `avatarUrl` back to the initials fallback. The topbar's own avatar (`components/layout/topbar.tsx`) reads the same `profile.avatarUrl`, so the change is reflected everywhere immediately rather than needing a separate sync step.

**Cross-page hash navigation (Statistics → `/revision#collections-section`) required a small fix to `ScrollRestoration`** (see below): it now skips restoring its own remembered scroll position whenever the destination URL carries a `#hash`, so the browser's native anchor-scroll isn't fought by — and doesn't lose to — the generic per-route scroll memory.

## Onboarding vs. Populated Dashboard

The dashboard renders one of two fundamentally different views, not one dashboard with empty-state placeholders bolted on — chosen purely from real data (`sessionList.length === 0` in `dashboard/page.tsx`), never a separate stored "is this user new" flag:

- **A genuinely new account (no session ever created) gets `OnboardingDashboard`** instead of the regular layout: a welcome hero naming the student and their already-chosen target exam (captured at signup — see below), the empty-state `StreakCard`, a single prominent "Start your first practice" CTA (which samples up to 10 **easy**-difficulty questions from their target exam, falling back to any difficulty for that exam, then to the whole bank, so it never dead-ends), secondary Question Bank / Custom Test entry cards, a "Getting started" checklist (choose exam / first session / first streak / first bookmark), and a "How JSMF works" explainer. It deliberately does **not** show the zeroed-out stat cards, a "Continue Practice" card with nothing to continue, or an empty "Recent activity" list — see the rationale below.
- **Once any session exists, the regular dashboard renders** — stat cards, `ContinuePracticeCard`, `StreakCard`, quick actions, recent activity, and focus areas, exactly as before. This is a two-stage system (new vs. populated), not the more finely graduated "first session / several sessions / mature" staging one product discussion considered — the extra gradations didn't have a crisp threshold ("several," "mature") and the two-stage version already satisfies the actual goal (a new student knows what to do in seconds; nothing empty is ever shown as if it were populated).
- **The target exam is asked once, at signup** (`targetExamId`) — the dashboard does not ask again. The signup form only shows the exam-picker question, and requires an explicit choice, when the plan the account is being created on unlocks more than one exam (`SubscriptionPlan.entitlements.examIds.length > 1`); a single-exam plan has nothing to choose between, so `targetExamId` is set to that one exam silently, and a plan with no exam access yet (Free) keeps a neutral default until the user upgrades. A later product iteration that lets a signup flow skip this could reuse the same onboarding hero to prompt for it there instead.

**Signup and login are deliberately different mock flows, matching what each implies in a real product**, and this is also how the mock now demonstrates both dashboard states on demand: **signup** resets `UserProfile` (`streakDays: 0`, fresh `joinedAt`, the entered name/exam) and hard-clears the practice-sessions, bookmarks, and best-streak stores (`resetSessions`/`resetBookmarks`/`resetBestStreak`), so it always lands on `OnboardingDashboard`, even in a browser that previously held seeded or real data from an earlier login. **Login** ("any email and password works," per the existing mocked-auth note) is treated as a *returning* user: it seeds plausible history (`buildSeedSessions`/`buildSeedBookmarkIds` from `lib/seed-demo-data.ts`) only if those stores are still empty, guaranteeing the populated/mature dashboard is always one click away for review, without ever overwriting real progress a signed-up account has actually made. Both actions live directly in `auth-store.ts`'s `signup`/`login`, calling the other stores' vanilla `getState()` — the standalone `SeedDemoData` component that used to auto-seed on every empty-store mount (regardless of signup vs. login) was removed, since that was exactly what made every new signup indistinguishable from a returning demo user.

## Streak & Engagement System

The streak feature exists to make the dashboard feel rewarding without tipping into gamification — no XP, levels, badges, or leaderboards, per an explicit product constraint (see Assumptions & Open Questions). It is built as a genuinely config-driven system rather than hardcoded thresholds/colors scattered through components:

- **`lib/streak-config.ts`** is the single source of truth: `STREAK_LEVELS` (nine tiers — new/warming/hot/blazing/legendary/elite/master/grandmaster/mythic at 0/3/7/14/30/45/60/90/120 consecutive days — each with its own distinct accent color, a 0–4 glow intensity, and whether the tier idles with a slow breathing pulse), `STREAK_MILESTONES` (7/14/30/50/100 days, each triggering a stronger-but-still-restrained ring-expansion celebration), and `DAILY_QUESTION_TARGET`. `getStreakLevel(days)` is the only lookup any component performs — nothing else hardcodes a threshold or a color. Every tier from 120 days onward shares the `mythic` tier's color, i.e. the palette caps rather than growing without bound.
- Each tier's accent is its own CSS custom property (`--streak-warming` through `--streak-120` in `globals.css`, tuned per light/dark mode), forming a deliberate, restrained color ramp — teal through blue for the early tiers, gold through bronze for the higher ones — so the badge is visibly, not just glow-wise, different at each stage. These tokens are independent of the accent-preset system (`data-palette`) described below, so the streak progression reads consistently regardless of which accent preset is selected.
- **`types.StreakState`** (`currentStreak`, `bestStreak`, `todayProgress`, `dailyTarget`, `lastCompletedDate`, `celebratedToday`, `isMilestone`, `nextMilestone`) is the one shape every streak-aware component consumes, assembled by the `useStreakState()` hook. A real backend needs only to return this shape directly for every UI component to keep working unchanged.
- **`StreakCard`** (dashboard) shows today's progress against the daily target, the current streak, and the historical **best streak** (which persists independently and never decreases when a streak resets — see the dedicated `useStreakStore`, `jsmf:streak` in localStorage — separate from `UserProfile.streakDays`, which is the live/current count). Its glow scales continuously with how much of today's goal is filled, not a hard on/off. It sits side by side with `ContinuePracticeCard` on the dashboard, both stretched to equal height regardless of which has more content.
- **Completing the daily goal** triggers a short sequence: the card briefly "bursts," a small badge visually detaches and travels (measured via `getBoundingClientRect`, animated with plain CSS transitions — no animation library) to the topbar streak chip, and lands with a pulse that increments the visible number — coordinated by an intentionally **non-persisted** `useStreakAnimationStore` (phase/source-rect/topbar-target/landed-signal), mounted once as `StreakFlyOverlay` in the authenticated app shell. The streak count itself updates immediately and independently of whether this animation ever plays, so it is correct even if interrupted (e.g. navigating away mid-flight).
- The animation store's `phase` has three states — `idle`, `pending`, and `flying` — not two. `pending` begins the instant completion happens (`beginPending`, called *before* the real count updates), and `flying` begins only once the badge actually starts moving, ~500ms later. Every display that freezes its count during the animation (`TopbarStreakChip`) does so for the entire `pending` + `flying` span, not just `flying`: the real count already changes at the start of `pending`, so freezing only during `flying` left a window where the topbar would flash the new number ahead of the animation, then revert, then re-advance on landing. `flightFromValue`, captured once by `beginPending`, is what every consumer reads to know what to freeze at, rather than each one tracking its own "last known count" — a per-consumer ref would itself have already advanced by the time `flying` starts.
- **`TopbarStreakChip`** reads the same level config as the dashboard card, so its color/glow/idle-pulse scale with the real streak everywhere it appears, and registers itself as the landing target for the fly animation. A small "i" info button next to the chip opens a click-triggered `Popover` (not a hover tooltip, so it works the same on touch) listing every tier's label, day range, and swatch, with the wearer's current tier highlighted — a mock-mode aid for reviewing the color ramp, labeled "Streak stages (mock preview)". The topbar doesn't render this chip at all while `streakDays === 0` — an empty "0-day streak" pill reads as a failed achievement rather than an invitation; `StreakCard`'s own empty state carries that invitation instead.
- **Demo-only replay behavior:** because this is a frontend-only mock with no backend to say "today's questions are done," `StreakCard` simulates reaching the daily goal on every dashboard visit **once an account already has a streak going**, and `DEMO_ALWAYS_CELEBRATE_ON_VISIT` in `streak-config.ts` bypasses the real once-per-day gating so the completion animation replays each time it is opened — useful for reviewing the feature. The real gating (`lastCompletedDate`/`celebratedToday`, wired but currently unused) activates with no other code changes the moment that one flag is set to `false`.
- **A brand-new account (`currentStreak === 0`) is deliberately exempt from that demo ramp** — otherwise merely visiting the dashboard would fabricate day one before any real question was ever answered, which would contradict the onboarding dashboard's own empty state ("Answer 10 questions to begin one"). Instead, `StreakCard` watches the same `todayProgress` used everywhere else (derived from real attempts made today, via `countAttemptsOnDay`) and calls `completeToday()` for real the moment it reaches `dailyTarget` — this is the actual, non-demo mechanism the ramp elsewhere is standing in for. Two easy-to-reintroduce bugs are worth flagging for anyone touching this code: (1) the triggering effect must depend on `todayProgress`, not just `currentStreak === 0`/`celebratedToday`, because `usePracticeStore` rehydrates from localStorage asynchronously — on a fresh page load the effect's first run can see a stale `todayProgress` of 0 before hydration finishes, and without that dependency, hydration completing moments later would never re-trigger it; (2) the ref that guards against double-firing must only be set *inside* the timer callback that calls `completeToday()`, never synchronously in the effect body before scheduling that timer — React's dev-mode StrictMode double-invokes effects (mount → cleanup → mount again) synchronously, and a zero-delay timer scheduled on the first pass gets cancelled by that cleanup before it can fire; if the guard ref were already set beforehand, the surviving second pass would wrongly see the work as already done and never reschedule it, so the completion would silently never happen. Both are exactly the failure mode this section's demo-ramp branch already avoided (by deferring into a timer callback), which is why mirroring that shape here matters.

## Mock Data Model

The mock prototype is built around the following core TypeScript entities:

- **Exam** — `id`, `name`, `shortName`, `description`, covering NEET-PG, FMGE, and INI-CET.
- **Subject** — `id`, `name`, `slug`, and `group`, where `group` is one of pre-clinical, para-clinical, or clinical; this grouping is what drives the grouped filter UI in the question bank.
- **Topic** — `id`, `subjectId`, `name`.
- **Option** — `id`, `text`, `imageUrl` (present in the type for forward-compatibility; unused by the seeded content, which relies on `stemFigure`/`explanationFigure` instead — see below).
- **Question** — `id`, `examId`, `year`, `subjectId`, `topicId`, `stem`, `stemFigure`, `options`, `correctOptionId`, `explanation`, `explanationFigure`, `difficulty`.
- **BookmarkEntry** — `id`, `questionId`, `createdAt`; bookmarks are persistent and independent of any particular session.
- **Attempt** — `questionId`, `selectedOptionId`, `isCorrect`, `timeSpentSec`, `answeredAt`.
- **TestSession** — `id`, `mode` (one of `browse`, `custom-test`, `bookmarks`, `wrong-questions`), `label`, `filters`, `questionIds`, `config` (including whether the session is timed and its duration in seconds), `flags`, `attempts`, `startedAt`, `completedAt`.
- **UserProfile** — `id`, `name`, `email`, `avatarUrl`, `targetExamId`, `joinedAt`, `currentPlanId`, `streakDays` (the live/current streak), `lastActiveAt`.
- **SubscriptionPlan** — `id`, `name`, `tagline`, `priceMonthly`, `priceYearly`, `entitlements` (comprising `examIds` and `features`), `highlight`.
- **StreakState** (derived, not stored — see Streak & Engagement System above) — `currentStreak`, `bestStreak`, `todayProgress`, `dailyTarget`, `lastCompletedDate`, `celebratedToday`, `isMilestone`, `nextMilestone`.
- **QuestionStatus** (derived) — `"correct" | "incorrect" | "unattempted"` per question, from the most recent attempt across all sessions; this is what the Question Bank's status filter/indicators and the Revision hub's slices are built on (`getQuestionStatusMap`, `getWrongQuestionFacets` in `lib/selectors`).

**Images are modeled as stylized placeholders, not real image files.** Rather than `stemImageUrl`/`explanationImageUrl` string fields pointing at real (or stock) images, a question carries an optional `stemFigure` / `explanationFigure` of shape `{ kind: FigureKind, caption: string }`, where `FigureKind` is one of `xray`, `ct`, `histology`, `ecg`, `clinical-photo`, `diagram`, or `chart`. A `FigurePlaceholder` component renders this as a clearly-labeled placeholder card (an icon matching the modality, a label, and the caption) rather than an actual radiograph, slide, or photo. This was a deliberate implementation choice: it satisfies the "images where required" requirement from [V1 Scope](./02-v1-scope.md) without needing real (and potentially license-encumbered) medical imagery for a mock, while still exercising the layout and information a real image would eventually occupy.

A deliberate modeling choice here is that wrong-question lists and all statistics are **derived, not stored**. They are computed by selector functions (`getWrongQuestions`, `getStatistics`, `getSessionSummary` in `lib/selectors`) operating over `Question[]`, `TestSession[]` (which carry the attempts and flags), and `BookmarkEntry[]`, rather than being written and maintained as their own persisted records. This avoids the class of bugs that comes from having the same fact — for example, "was this question answered incorrectly" — represented in two places that can drift out of sync.

On seeding volume: all nineteen MBBS subjects are present with full metadata and topics, so that filtering feels realistic across the entire subject list. Six "hero" subjects — General Medicine, General Surgery, Pathology, Obstetrics & Gynaecology, Pediatrics, and Pharmacology — carry roughly 16 questions each; the remaining thirteen subjects carry roughly 7 each, for a seeded bank of about 187 original questions in total, each with a mix of difficulty levels and a spread across all three exams and the last five years, with a subset carrying a `stemFigure`/`explanationFigure`. These hero subjects back the landing-page demo and the default custom-test flows. All seeded content is original, textbook-standard-fact medical-exam-style text — it is never scraped or reproduced from real NEET-PG, FMGE, or INI-CET content, nor from any competitor's content, consistent with the content-integrity principle described in [Product Vision](./01-product-vision.md) and [Content Pipeline](./04-content-pipeline.md).

## Scroll Restoration

**Returning to a page you scrolled down on should never dump you back at the top.** Next.js's App Router only restores scroll position automatically for genuine browser back/forward (history POP) navigations — most "return to where I was" actions in this app are actually a regular forward push to a remembered href (e.g. practice's "Save & Exit" link, built from `sourceHref` — see "Continue where you left off" below), which Next treats as a fresh navigation and scrolls to the top by default. `ScrollRestoration` (`components/common/scroll-restoration.tsx`, mounted once in the root layout so it covers every route in the app, marketing and app shell alike) fixes this generically rather than per-page: it keeps an in-memory `Map` of the last-known scroll position per `pathname + search`, continuously updated on every `scroll` event (not captured once on unmount, since there's no reliable hook for "just before this route goes away") and reapplied via `window.scrollTo` across a handful of `requestAnimationFrame` retries whenever the route changes — the retries matter because a route's real height often isn't final on first paint (async Zustand store hydration, charts, etc.), so a single immediate `scrollTo` can land short on a page that's still growing under it.

## Question and Session Sorting

Three pages let the student re-order what they're looking at: the Question Bank, the Revision hub, and History. Each needed a different scope, so this is deliberately three separate option sets sharing one underlying model, rather than one universal sort dropdown everywhere.

`lib/question-sort.ts` defines the full `QuestionSortOption` union (15 values: recency of last attempt in either direction, newest/oldest exam year, subject name A–Z/Z–A, and five pairs of recency scoped to a specific fact — wrong, bookmarked, correct, and collected) plus `buildQuestionSortContext()`, which derives every per-question timestamp/count a sort could need (last attempt, last wrong attempt, incorrect-attempt count, last correct attempt, bookmarked-at, and collected-at — the `createdAt` of the most recently created collection containing that question) from sessions, bookmarks, and collections in one pass, and `sortQuestions()`, a single comparator switch consuming that context. Recency-based comparisons work directly on ISO timestamp strings (they compare correctly without parsing) and always sort a question lacking that property to the end, in either direction — a question with no attempts isn't "the oldest attempted," it simply doesn't have the property being sorted on. "Subject A–Z/Z–A" sorts by **subject name**, not the question's own text — a question has no short name, and alphabetizing raw stem paragraphs would read like a phone book, whereas grouping by subject name is the natural reading of a name-based sort for a question list. This is named "Subject" rather than "Name" specifically because it sorts by subject — unlike History's "Name A–Z/Z–A" below, which really does sort by a name (the session's own label) and keeps that wording.

- **Question Bank** (`question-bank/page.tsx`): the narrowest case — just `newest-exam-year` / `oldest-exam-year` / `name-az` / `name-za` (`QUESTION_BANK_SORT_OPTIONS`), applied after the existing filter/status pipeline. Defaults to "Most recent — newest exam/year first."
- **Revision hub** (`revision/page.tsx`): each of the four sections (Wrong Questions, Bookmarked, Reinforce, Collections) has its own **local** sort dropdown scoped to only the options relevant to that section (`REVISION_SECTION_SORT_OPTIONS`) — e.g. "Recently bookmarked" only appears in the Bookmarked section's list, "Collected recently/earliest" only in Collections'. Each defaults to "Recently attempted" (a real `QuestionSortOption`, like every other option in the list) rather than a placeholder. This page briefly had a page-header "Sort all sections" dropdown plus a "Same as global sort" pseudo-option (`"inherit"`) in each section's own dropdown that deferred to it — both were removed once the header control was cut as visual clutter, since "Same as global sort" no longer meant anything without a control to change what "global" was; each section's sort state is now a plain `QuestionSortOption`, no indirection.
- **History** (`history/page.tsx`): sorts completed *sessions*, not individual questions, so it uses its own local `SessionSortOption`/`sortSessions()` rather than the question-level module — "Highest/Lowest accuracy" reads that session's own accuracy, "Recently/Oldest wrong" reads the most recent incorrect attempt *within* that session, "Unattempted" ranks by how many of the session's questions were left unanswered, and "Name A–Z/Z–A" sorts by the session's own label. Defaults to "Recently wrong."

A shared `SortDropdown` (`components/common/sort-dropdown.tsx`) renders all of the above as a consistent trigger-plus-checklist popover (not a native `<select>`, to match the app's other filter popovers), generic over whatever string-literal option type is passed in. Each option can carry an optional `group` id — opposite-direction pairs of the same underlying sort ("Recently attempted"/"Least recently attempted", "Subject A–Z"/"Subject Z–A," etc.) share one, so the popover can give each pair its own subtle background tint and a long option list stays scannable at a glance rather than reading as one undifferentiated column of text. The tints cycle through the chart palette (`chart-1`–`chart-5`, at low opacity) specifically because those tokens are the app's only *purely categorical* colors — unlike `success`/`error`/`accent`, they carry no meaning of their own, so reusing them here doesn't accidentally imply "this sort is good" or "this one is a warning." Groups aren't always a strict pair, either — "wrong" is a trio: "Most incorrect attempts" shares that tint with "Recently wrong"/"Oldest wrong" as the same underlying concept, despite having no opposite direction of its own. An option that shares no group with anything (History's "Unattempted", the only one on the app) still gets its own standalone tint, keyed off its own value. `QUESTION_SORT_GROUPS` (question-level) and `SESSION_SORT_GROUPS` (History's session-level) hold this grouping.

The section also gained a "Year" filter (`wrongYears`) next to "All Exams," reusing `RECENT_YEARS` and the exact same label-less `MultiSelectPopover` pattern the Question Bank's filter panel uses for its own Year filter — both narrow `wrongExamPool` by `q.year` before it reaches `getWrongQuestionFacets`.

The Wrong Questions section's tabs were consolidated from four (All wrong / Recently wrong / Never corrected / By subject) to three — **"All wrong" and "Recently wrong" were the same underlying concept at two different, arbitrarily-fixed points on one continuum** (no filter vs. a hardcoded last-7-days filter), so once the date range below became fully configurable there are no longer two distinct tabs' worth of behavior, just one "Wrong" tab whose scope the always-visible date range controls. The `Mode` type dropped `"all"`/`"recent"` in favor of a single `"wrong"`. That date range is independent of the fixed 7-day window the Reinforce section still uses for its own recent/not-revisited split (the two were never the same concept and are now visibly decoupled, not just internally). A single-select `MultiSelectPopover` dropdown ("Last 7/14/30/90 days," "All time," or "Custom range" — `singleSelect`, sitting alongside the Exam/Year dropdowns above the question list rather than as a separate pill row) sets `recentWrongPreset`/`recentWrongFrom`/`recentWrongTo`, which resolve to a `DayRange` (`{ from, to? }` in `lib/selectors`) passed into `getWrongQuestionFacets`, and **defaults to "All time"** so the "Wrong" tab reads exactly like the old "All wrong" tab did on first visit — narrowing it down to what used to be a separate "Recently wrong" tab is now just picking a shorter preset. "All time" resolves to `{ from: null, to: null }` rather than `null` — the distinction matters: a `null` range tells the selector not to compute the `recent` slice at all (the state before any range has been meaningfully chosen, e.g. an empty custom range), while an unbounded-but-present range computes it as every wrong question. That selector's third parameter changed from a bare "since" string to this `DayRange` specifically to support an upper bound as well as a lower one — a preset window only ever needs "since N days ago," but a custom range needs both ends. The section's blurb line and empty-state copy describe whichever range is actually active (a preset's day count, or the literal custom dates) rather than a hardcoded "last 7 days."

**That same filter shape — a two-tab "recent vs. by subject" split, an Exam/Year row, and a date-range dropdown with a describing sentence — was then generalized to all four Revision sections**, not just Wrong Questions, since the request was explicitly for a consistent format across the page. Three shared, stateless components now back all four: `ExamYearFilterRow` (the Exam + Year `MultiSelectPopover` pair), `DateRangeFilterRow` (the small single-select date preset dropdown, its description text, and the custom-range calendar when "Custom range" is picked), and `groupBySubject` (a plain grouping helper, not a component). `DatePreset`/`DATE_PRESETS`/`computeDateRange`/`isWithinRange`/`dateRangeDescription` were pulled out of the Wrong-specific code that originally only served that section and made generic (parameterized by a `verb` like "Got wrong"/"Bookmarked"/"Answered correctly"/"Added" and an all-time fallback sentence) so each section gets its own independent state (`bookmarkedExamIds`, `reinforcePreset`, `collectionsFrom`, etc.) while sharing one implementation. Bookmarked's two tabs are "Recently Bookmarked" (filtered by the bookmark's own `createdAt`) and "By subject"; Reinforce's are "Recently attempted" (filtered by each question's latest *correct* attempt date, via `getLatestAttemptByQuestion`) and "By subject" — this replaced the old fixed 7-day "recent/not-revisited" split entirely, the same consolidation reasoning as Wrong Questions' tab merge; Collections' are "Recently added" and "By subject". As with Wrong Questions, the exam/year filter and the "By subject" grouping apply *before* the date range and ignore it, while the date range only narrows the "recent" tab's list — so the top-of-page stat tiles (which read the exam/year-filtered-but-not-date-filtered pool: `bookmarkedPool.length`, `reinforcePool.length`) stay stable as someone narrows the date range, exactly mirroring how the Wrong tile already worked off `facets.all` rather than the date-scoped `facets.recent`. Collections' date filter has one honest limitation worth knowing if it's revisited: mock `Collection` data only timestamps the collection as a whole (`createdAt`), not each question's individual add date, so "added in the last N days" filters the entire selected collection at once against that one timestamp rather than per question — the collection's whole question list either passes the filter or none of it does.

A custom range is picked via a bespoke calendar `DateRangePicker` (`components/common/date-range-picker.tsx`, built on `date-fns` + the shared `Popover`) rather than a pair of native `<input type="date">` fields — those were functional but looked and behaved inconsistently across browsers and didn't visualize the selected span the way a calendar grid does. It supports click-click range selection with a hover preview of the in-progress span, month navigation, and explicit "Clear"/"Apply" actions (the draft selection only commits on "Apply," and resets to the last committed value if the popover is closed without it, so an abandoned in-progress selection never leaks through). The same component now backs History's custom-range filter too. One rendering detail worth knowing if this is touched again: the tinted band that visually connects the two selected endpoints is drawn on each day's *outer grid cell* (which fills the full column width), not on the smaller circular day button itself — drawing it on the button left visible gaps between cells at the button's fixed size, since the button doesn't stretch to fill its cell.

The Wrong Questions section also gained an "All Exams" filter (`wrongExamIds`), scoped to the whole section rather than just the "Recently wrong" tab — it restricts the question pool passed into `getWrongQuestionFacets` before any of the four tabs (All/Recently/Never corrected/By subject) compute their counts. It reuses the same `MultiSelectPopover`/"All Exams" pattern as the Question Bank and Custom Test filter panels (empty selection = unfiltered, matching that convention) rather than a bespoke control, for visual and behavioral consistency with the exam filter students already know from those screens.

## Session Results Filtering

On a completed session's results screen (`practice/[sessionId]/results/page.tsx`), the Correct/Incorrect/Unattempted stat tiles are clickable and act as a filter on the question list below (the fourth tile, "Time taken," isn't a question status and stays non-interactive). Clicking a tile toggles it: clicking again — or clicking "Clear filter" in the hint line that appears once a filter is active — returns to showing every question. A tile with a zero count renders as a plain (non-clickable) tile, since there's nothing to filter to. The filtered list still shows each question's real position (`Q{i+1}`, linking to `/practice/{id}?i={i}`) rather than renumbering from 1, since that index is a real position in the original session, not a property of the filtered view. An empty state ("No {filter} questions") only shows when a filter is active and genuinely matches nothing (not reachable in practice, since a zero-count tile isn't clickable in the first place — kept as a defensive fallback).

## State Management

State is managed with **zustand** rather than React Context, because the state that changes most frequently in this product — a practice session's per-question answers, flags, and a possibly-ticking timer — updates often enough that Context would trigger broad, unnecessary re-renders across the tree.

The stores are:

- **`useAuthStore`** — holds a mock `isAuthenticated` flag and the current `UserProfile` (including `currentPlanId`); `login`, `signup`, `logout`, and `updateProfile` simply set local state (and persist it to `localStorage`) rather than talking to any real backend. **Implementation note:** plan changes are handled here too, via an `upgradePlan(planId)` action on this same store, rather than through a separate subscription store — since the mock's only subscription state is "which plan id is the current user on," folding it into the profile avoided a second store with almost nothing in it. A real backend-backed implementation would likely still want subscription/entitlement state to live in its own service, per [Architecture](./03-architecture.md); this is purely a mock-stage simplification.
- **`usePracticeStore`** — holds the record of sessions and exposes `createSession`, `submitAnswer`, `toggleFlag`, and `finishSession`. This store is persisted via zustand's `persist` middleware to `localStorage`, and it is the single source of truth that history, wrong-questions, and statistics all read from. Its persistence is versioned with a `migrate` step (see below).
- **`useBookmarksStore`** — holds a persisted `BookmarkEntry[]` and a `toggleBookmark` action.
- **`useStreakStore`** — persists only `bestStreak`, with a `recordStreak(currentStreak)` action that takes the max; the live/current streak lives on `UserProfile.streakDays` instead, since best-streak's "never decreases" rule is a genuinely different lifecycle from a live counter.
- **`useStreakAnimationStore`** — deliberately **not** persisted (see Streak & Engagement System above): coordinates the completion fly/land animation across `StreakCard`, `StreakFlyOverlay`, and `TopbarStreakChip`, which don't otherwise know about each other.

**A note on persisted-store migrations.** `useAuthStore`'s persistence carries a `version` and a `migrate` function, added after a real bug: a demo profile default (`currentPlanId`) was changed in code, but a browser that had already persisted the old value kept showing it indefinitely, because the persisted copy silently wins over the new code-level default on every future load. The fix — bump `version`, migrate old persisted state to the new default — is the general pattern for any future change to a demo default in `DEMO_USER` or similar, not just that one field.

Every persisted store exposes a `hasHydrated` flag (set once zustand's `persist` middleware finishes reading from `localStorage`), and every page that reads one of these stores waits for it before rendering real content — otherwise a page could briefly flash the store's default empty state before the real persisted data loads. A shared `safeLocalStorage` helper (`store/persist-storage.ts`) makes the underlying storage a no-op during server rendering (where `localStorage` doesn't exist) and the real `window.localStorage` in the browser, so the same store code works in both environments without special-casing.

Derived data — `getWrongQuestions`, `getStatistics`, `getSessionSummary`, and similar — is computed via plain selector functions rather than being kept in its own store, consistent with the "derived, not stored" principle described in the data model section above.

Separately, URL search parameters are treated as the source of truth for anything that should be navigable or shareable — question-bank filters and the current question index within a session both live there rather than purely in a store. One practical benefit of this, combined with everything being in-memory mock data, is that question-bank filtering can update instantly against in-memory arrays with no network round-trip at all.

Finally, the mock is deliberately built to make a later transition to a real backend cheap: all data access is wrapped behind small functions — `getQuestions(filters)`, `createTestSession(config)`, `submitAnswer(...)`, and similar — that are written as `async` even though today they resolve synchronously against local arrays and stores. Because call sites already `await` them, swapping their internals for real `fetch()` calls against the future NestJS backend described in [Architecture](./03-architecture.md) will require no changes at the component or page level.

## Design Tokens

**Color.** The palette centers on a deep ink-navy as the primary color — trustworthy and academic, used sparingly rather than covering large surfaces — set against a warm off-white "paper" background rather than a stark white, which is meant to evoke a printed journal and is easier on the eyes across long study sessions. A full cool-gray neutral scale handles borders, secondary text, and surfaces. Correct and incorrect states use a muted, calmer green/red rather than saturated pure colors, since a student sees them hundreds of times in a single session.

**The accent color settled on teal** (not the amber/gold originally planned), used the same restrained way — kicker pills, badges, progress bars, active nav item, correct-answer indicators, bookmarks, primary-button hover — deliberately *not* spread across headings or large surfaces ("the reason your current screenshots look premium is the restraint" was the explicit product direction that shaped this). The heading/body/button-background ink color is separately configurable from the accent — see the theme picker below.

**Theme picker (dev-only, `components/dev/theme-palette-picker.tsx`).** A floating "Theme" control, present on every page, that lets a reviewer compare accent-color and ink-color options live without touching code — built so a second reviewer (e.g. a stakeholder on a separate device) can form and share an opinion before a final palette is locked in. It exposes two independent choices, applied as `data-palette`/`data-primary` attributes on `<html>` with corresponding attribute-scoped overrides in `globals.css`, each persisted to that browser's `localStorage` only (not shared between visitors):
- **Accent color** — Navy + Teal (current default), Navy + Emerald, Navy + Amber (the original plan), or Navy only (no accent at all, a monochrome baseline for comparison).
- **Primary / text color** — Navy (current default), Charcoal (neutral, no blue tint), Slate blue (lighter, reads more clearly as blue), or Indigo (a deeper purple-blue).

This tool is explicitly not part of the real product and is easy to delete once a final palette is chosen; it exists only to make that final choice a live comparison rather than a screenshot-and-guess exercise.

**Typography.** The type system is deliberately split into two tiers. "Reading" contexts — the question stem, its options, its explanation, and long-form marketing copy — use `Source Serif 4` at a larger base size of 17–18px with a generous 1.6–1.7 line-height. Using a serif for the reading surface is a deliberate differentiator from Marrow and PrepLadder, both of which are sans-serif throughout, and it reinforces an "academic journal" positioning while genuinely reducing eye strain across long reading sessions compared to a sans body set at length. "UI/data" contexts — the sidebar, tables, stat cards, and filters — instead use `Plus Jakarta Sans`, a geometric-humanist sans chosen specifically to avoid the generic "Inter on every SaaS product" look, at weights 500/600/700 for navigation, buttons, stat numbers, and headings, set at a tighter 14–15px base for information density. Headings follow a modular scale of roughly 1.2–1.25. A small, deliberately sparing accent role is reserved for `JetBrains Mono`, used only for timer, score, and streak numerals, as a "precision instrument" touch.

**Spacing and layout.** The project uses Tailwind's default 4px-based spacing scale, with generous vertical rhythm on marketing sections. App content is capped at a max-width of roughly 1200–1280px, alongside a fixed 260px sidebar (72px when collapsed to its icon rail). The practice screen's reading column is capped at 720–760px and centered regardless of viewport width — as noted above, the single highest-leverage readability decision on that screen. Surfaces use crisp 8–12px corner radii rather than the "bubbly" 20px-plus radii seen elsewhere, favor flat surfaces with subtle borders over heavy drop shadows, and avoid gradients throughout except for possibly one restrained hero background treatment on the landing page.

## Assumptions & Open Questions

The following assumptions are treated as settled for this stage of the project but are worth surfacing explicitly, since several of them are the kind of thing a stakeholder should be able to confirm or challenge:

- **Dark mode** is not fully polished in v1, but `next-themes` and the CSS-variable token system are wired in from day one specifically so that a proper dark mode is a cheap follow-up rather than a retrofit.
- **Responsive scope** is desktop-first and desktop-primary, reflecting that this is fundamentally a laptop-session study product. There is no dedicated mobile-app-grade polish pass for this web mock — the real mobile experience is expected to come from the separate Flutter app described in [Architecture](./03-architecture.md), not from a fully mobile-optimized web build. A targeted mobile-viewport (375–430px) bug pass has been done on top of that baseline, though: the app shell's `Topbar` already collapsed the sidebar into a `Sheet`-based hamburger menu at `md:hidden`, but `MarketingHeader` did not — its nav links (Exams/How it works/Features/FAQ/Pricing) were `hidden md:flex` with no mobile alternative, so it now gets the same `Sheet` hamburger pattern as the app shell. The shared `TabsList` primitive (`src/components/ui/tabs.tsx`) also let a wide horizontal tab row (e.g. Question Bank's status tabs) push the whole page into horizontal scroll at narrow widths; it now scrolls internally (`max-w-full overflow-x-auto` on the horizontal variant) instead. These are bug fixes, not a mobile design pass — no new breakpoints or token changes were introduced.
- The project is a **single Next.js app using route groups**, rather than a separate marketing subdomain, purely for simplicity at this stage; this can be split apart later if there is a reason to.
- **Auth is entirely mock.** There is no real password hashing, session handling, or JWT issuance; signup and login accept any input and simply set local state, and the forgot/reset-password flow is a UI-only simulation with no real email being sent. None of this should be treated as security-reviewable — it is a UI stand-in, not a real authentication implementation, consistent with the "Current Stage" description in [V1 Scope](./02-v1-scope.md).
- **Subscription and payment are UI-only.** Clicking "Upgrade" or "Switch plan" simply calls `upgradePlan()` on `useAuthStore`, flipping local state; there is no real billing integration behind it.
- **Content originality** is a hard requirement even for placeholder content: every seeded question must be original or clearly placeholder-style, never copied from real exam banks or from competitor products, in keeping with the content-integrity principle in [Product Vision](./01-product-vision.md).
- **Images** are represented as stylized placeholders (see `FigurePlaceholder` in the Mock Data Model section above) rather than real image files, specifically to avoid needing licensed medical imagery for a mock; a real image upload and CDN pipeline is out of scope for the mock.
- **Internationalization** is not attempted — the product is English-only for v1.
- **Testing** does not require an automated test suite at this pure-UI prototype stage, beyond type-checking and linting.
- **Restraint is a standing design constraint, not just an initial choice.** Both the accent color and any dashboard motivational features (streaks, progress, greetings) are deliberately scoped to a small, repeatable set of places rather than spread across the product or turned into game mechanics (no XP, levels, badges, or leaderboards) — this was stated explicitly as the reason the UI reads as premium, and should keep shaping any new visual or motivational addition.
- **The streak completion animation replays on every dashboard visit** in the current mock, rather than once per real day — a deliberate, flagged (`DEMO_ALWAYS_CELEBRATE_ON_VISIT`) simplification so the feature is easy to review without waiting a day between checks; see Streak & Engagement System above for how this becomes the real once-per-day behavior with a single flag flip.
- The **practice-session timer**, despite everything else being mocked, can be genuinely functional as a real client-side countdown, since it requires no backend dependency to work correctly.
